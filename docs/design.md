# 설계와 대안 비교

목표는 문제 풀이와 짧은 기록을 매일 지속하면서, Git 브랜치·push·PR·코드리뷰를 익히는 것입니다.
형식 정리와 집계는 자동화하고, commit·push·리뷰는 참여자가 직접 경험하도록 구성했습니다.

## 저장 방식

| 방식 | 장점 | 고려할 점 | 결정 |
| --- | --- | --- | --- |
| Markdown 한 파일에 설명과 코드 전부 작성 | 한 화면에서 읽기 편함 | 실행 시 코드를 추출하거나 중복 관리해야 함 | 간단한 개인 노트에 적합 |
| 코드의 긴 주석으로 문제·메타데이터 작성 | 파일 하나로 끝남 | 언어별 양식이 달라지고 본문·표를 읽기 불편함 | 선택하지 않음 |
| 문제 폴더에 README + 코드 + JSON | 설명 읽기, 코드 실행·리뷰, 자동 집계에 각각 적합 | 파일이 늘어남 | 생성 CLI로 반복 작업 해결 |

직접 작성할 곳은 풀이 코드와 README의 짧은 세 항목입니다.
JSON은 도구가 만들고 갱신합니다. 시간·난이도·태그·회고는 선택 사항입니다.
메타데이터와 설명은 서로 역할을 나누며 README에 코드를 중복 저장하지 않습니다.

문제 원문을 자동 수집하는 방식도 가능하지만 사이트마다 페이지 구조·인증·접근 방식이 다릅니다.
우선은 네트워크 연결 없이 URL에서 문제 식별자를 추출하고 제목만 입력하도록 했습니다.
문제 본문은 원문 링크와 짧은 자기 요약으로 남깁니다. 템플릿에 원문·제약·입출력 표를 추가해도 됩니다.
지원 플랫폼을 늘리려면 `study.py`의 `identify()`에 URL 규칙을 추가합니다.

## 폴더와 PR의 단위

| 구성 | 읽기·운영 특성 |
| --- | --- |
| 사람 → 문제 | 개인별 전체 기록은 편하지만 오늘 팀 전체 기록이 흩어짐 |
| 문제 → 사람 | 같은 문제 비교에 좋지만 서로 다른 문제를 매일 푸는 흐름과 다름 |
| 날짜 → 사람 → 문제 | 오늘의 팀 활동을 모아보고, 사람별 일일 PR과 폴더가 일치함 |

선택한 구조는 `records/YYYY/MM/DD/사람/플랫폼-문제번호/`입니다.
전역 보고서가 개인별 통계와 문제별 인덱스를 제공해 날짜 중심 구조의 탐색 약점을 보완합니다.
여러 언어의 풀이는 같은 문제 폴더에 추가 파일로 둘 수 있지만 하루 문제 수는 한 번만 셉니다.
다른 날 재풀이는 복습 활동으로 다시 셉니다. 누적 완료는 서로 다른 문제 수가 아니라 완료 기록 수입니다.

개인 브랜치를 계속 재사용하면 merge 방식과 이전 리뷰 상태에 따라 변경이 누적되기 쉽습니다.
`study/사람/날짜`로 매일 최신 main에서 분기하고, 하루 5문제는 PR 하나로 묶습니다.
네 사람 기준 하루 PR 4개로 리뷰 부담을 제한하고, 코드 줄 단위 의견을 남길 수 있습니다.
GitHub는 PR 승인과 상태 검사 통과를 병합 조건으로 설정할 수 있습니다.
[GitHub 공식 문서: 보호 브랜치](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 자동화 흐름

1. `init`: 로컬 기본값 저장. `new`: 첫 등록, URL 정규화, 코드 복사/생성, README/JSON/일일 목록 생성.
2. `done`: 필수 설명·코드 확인 후 solved 상태 저장. 채점 사이트 정답 확인은 작성자가 수행.
3. `prepare`: 기록 검증, 목표와 추천 리뷰어 계산, `.study/PR.md` 및 Git/PR 명령 생성.
4. push/PR: `study-check`가 형식·파일 경로·목록 일관성·일일 PR 범위를 확인.
5. main push/매일 예약: 전체 보고서를 생성하고 `progress` 브랜치의 README만 갱신.

GitHub CLI의 `--body-file`과 `--reviewer`로 자동 생성한 본문을 사용해 PR을 만들 수 있습니다.
도구는 실행 명령을 출력하며, 사용자는 직접 push와 PR 생성 단계를 수행합니다.
[GitHub CLI 공식 매뉴얼](https://cli.github.com/manual/gh_pr_create)

main의 공용 통계 파일을 매번 참가자 PR에서 수정하면 같은 줄을 동시에 수정하는 충돌이 생깁니다.
일일 목록은 사람별 폴더에, 전역 보고서는 `progress` 전용 브랜치에 둡니다.
봇은 main에 직접 커밋하지 않아 리뷰 필수 설정과 충돌하지 않습니다.
보고서 게시 스크립트는 fast-forward push만 사용하고 동일 내용이면 커밋을 생략합니다.
PR 검사는 읽기 권한, main 보고서 갱신만 쓰기 권한을 사용합니다.
기여자가 제출한 풀이 코드는 CI에서 실행하지 않습니다.

Actions에서는 PR/push/예약 이벤트로 실행을 구분하고, 실행 요약에 Markdown 보고서를 표시합니다.
예약 실행은 기본 브랜치의 workflow를 사용합니다.
[이벤트 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows),
[실행 요약 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-job-summary)

## 다른 레포에 재사용

독립적인 스터디를 시작하려면 GitHub의 Template repository 기능으로 파일 구조를 재사용할 수 있습니다.
원본 스터디로 다시 PR을 보낼 목적이면 fork를 사용합니다. Template로 생성한 저장소는 이력이 독립적입니다.
[GitHub 공식 문서: 템플릿 저장소](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-template-repository)

양식만 필요하면 `templates/problem.md`를 복사하고 변수 부분을 채워도 됩니다.
이 파일은 프로젝트의 문서 템플릿이며 별도 에디터 플러그인이나 유료 서비스가 필요하지 않습니다.

## 현재 범위와 확장 시점

기본 목표는 매일 5문제이며 날짜는 KST입니다. 사람별 목표 변경 이력을 보존합니다.
휴무일·요일별 목표·탈퇴 기간은 아직 별도 모델이 없습니다. 시작일 이후 매일 집계합니다.
목표 미달은 PR 실패가 아니며, 기록의 완성도와 리뷰 흐름을 우선합니다.

보고서에는 최근 14일 표와 전체 문제 목록이 있습니다. 기록이 수만 개로 늘면
문제 목록을 월별 파일로 분리하거나 검색 화면을 추가할 수 있습니다.
첫 버전에는 별도 웹 서버·DB·로그인·채점 서버를 두지 않아 설치와 유지 부담을 줄였습니다.
